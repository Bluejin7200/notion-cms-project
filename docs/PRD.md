# 지급 요청·승인 트래커 MVP PRD

## 🎯 핵심 정보

**목적**: Notion에 흩어진 지급 요청의 승인·지급·반려 처리와 지급 일정(연체 포함)을 한 화면에서 관리한다.
**사용자**: 수익 지급·집행을 처리하는 재정 관리 담당자 (1인 또는 소수 팀).

**전제**
- 지급 요청 **등록은 Notion 화면에서만** 한다. 웹앱에는 등록 폼이 없다.
- 웹앱은 조회와 **상태 변경(승인 / 지급완료 / 반려)** 만 담당한다.
- 기존 "주문" 예제 화면은 **지급 요청 화면이 대체**한다 (주문 메뉴·페이지·목업 데이터 제거, 목록 패턴만 재사용).

## 🚶 사용자 여정

```
1. 로그인 페이지 (미인증 상태로 대시보드 계열 접근 시 자동 이동, 원래 페이지 정보 유지)
   ↓ 로그인 성공 (데모 인증)
2. 대시보드 페이지 (요약 확인)
   ↓ 연체 카드 / 상태별 건수 클릭 → 해당 조건이 적용된 목록으로 이동
3. 지급 요청 목록 페이지 (검색·상태 필터·페이지)
   ↓ 행 클릭
4. 지급 요청 상세 페이지 (증빙 확인)
   ↓ 현재 상태 확인
   [요청]   → 승인 / 반려(사유 입력 필수)
   [승인]   → 지급완료 / 반려(사유 입력 필수)
   [지급완료·반려] → 변경 버튼 없음 (읽기 전용)
   ↓ 처리 성공 (Notion 갱신, 처리일 기록)
5. 상세 페이지 갱신 표시 (목록·대시보드는 다음 조회 시 최신 반영)

- 로그인 상태로 로그인/회원가입 페이지 접근 → 대시보드 페이지로 이동
- 없는 지급 요청 또는 Notion 조회 실패 → 상세 페이지 안에서 오류 안내 + 목록으로 돌아가기
```

**상태 전이 규칙**

| 현재 상태 | 가능한 처리 | 비고 |
|-----------|------------|------|
| 요청 | 승인, 반려 | 반려 시 사유 필수 |
| 승인 | 지급완료, 반려 | 지급 전 취소를 위해 승인 후 반려 허용, 사유 필수 |
| 지급완료 | 없음 | 최종 상태. 정정은 Notion에서 직접 수정 |
| 반려 | 없음 | 최종 상태. 재요청은 Notion에서 새 요청으로 등록 |

- 허용되지 않은 전이(예: 요청 → 지급완료)는 서버에서도 거부한다. 화면 버튼 숨김만으로 막지 않는다.
- 처리일은 **마지막 상태 변경 시점의 오늘 날짜(한국 시간)** 로 기록한다 (승인일은 별도 보존하지 않음).

### 3. MVP 이후 기능 (제외)

- 웹앱 내 지급 요청 등록·수정 폼: Notion 입력으로 확정
- 승인일/지급일 별도 이력, 변경 이력 로그: 처리일 1개로 단순화
- 알림(이메일·슬랙), 다중 사용자 권한(요청자/승인자 분리): 데모 인증 한계
- 금액 합계 엑셀 내보내기, 분류별 통계 차트
- 목록 내 일괄 승인
- 지급완료·반려 건의 상태 되돌리기
- 예제 페이지와 FAQ 등 스타터킷 마케팅 메뉴: 변경 없이 유지하되 MVP 범위 밖

## 📱 메뉴 구조

```
📱 공개 메뉴
├── 🏠 홈 — F013
└── 👤 로그인 / 회원가입 — F010

🔐 로그인 후 메뉴 (대시보드 사이드바)
├── 📊 대시보드 — F005, F006, F007, F009, F011
├── 💸 지급 요청 (기존 "주문" 메뉴 대체) — F001, F002, F003, F004, F007, F008, F009, F011
├── ⚙️ 설정 — F012, F011

```

- 지급 요청 상세 페이지는 별도 메뉴 없이 지급 요청 목록 페이지의 행 선택으로만 진입한다.
- 기존 상단 메뉴의 기능·예제·FAQ는 스타터킷 그대로 두며 MVP 범위에서 다루지 않는다.

## 🗄️ 데이터 모델 (Notion 데이터베이스)

### 지급 요청 (유일한 데이터베이스)

|------|------------|------|

| 수령처 | rich_text | 지급 받는 곳. 검색 대상 |
| 계좌 | rich_text | **마스킹 값만 저장** (예: 국민 ***-1234). 원문 계좌번호 입력 금지 |
| 금액 | number | 원 단위 정수. 요약 합계 계산 대상 |
| 지급 예정일 | date | 주/월 합계·연체 판단 기준 (한국 시간 기준 날짜) |
| 상태 | status | 요청(기본) / 승인 / 지급완료 / 반려. 웹앱이 변경하는 유일한 상태 값 |
| 분류 | select | 정산금 / 용역비 / 경비 / 기타 |
| 증빙 | url | 증빙 문서 링크 |
| 반려 사유 | rich_text | 반려 시 웹앱이 기록 |
| 처리일 | date | 마지막 상태 변경일. 웹앱이 기록 |
| 메모 | rich_text | 자유 메모 (Notion에서 입력) |

**타입 선택 이유**
- 상태: 요청 → 처리 흐름이 명확해 status가 적합하나, 옵션 구성과 API 쓰기 제약이 있어 select로 대체 가능성을 열어 둔다.
- 증빙: files는 Notion 업로드 파일 URL이 약 1시간 후 만료되므로 영구 링크가 되는 url을 선택한다.
- 금액: number(원 포맷). 합계를 서버에서 계산한다.
- 계좌: 마스킹 문자열만 다루므로 rich_text.

**prd-validator 검증 대상**
1. 상태를 status와 select 중 무엇으로 쓸지, API로 status 값 변경 가능 여부와 옵션 이름 일치 처리
2. Notion은 커서 기반 페이지네이션인데, 페이지 번호 방식(nuqs의 page)을 어떻게 맞출지 (전체 조회 후 서버 페이징 vs 커서 저장)
3. 제목·수령처·요청자 동시 검색을 or 필터로 구성 가능한지, 한글 부분 일치 동작
4. 대시보드 집계(주/월 합계, 연체)를 전체 조회 후 서버 계산하는 방식의 건수 한계와 캐시·갱신 시점(상태 변경 직후 반영)
5. 상태 변경 시 동시 수정 충돌 대응 (처리 직전 현재 상태 재조회로 충분한지)
6. Notion SDK(`@notionhq/client`)가 현재 package.json에 없으므로 추가 필요, 버전·data source 방식 확인
7. 연체 기준에서 반려를 제외한 판단(요구는 "지급완료가 아닌 건"이며, 반려는 지급 대상이 아니라 제외로 가정)
